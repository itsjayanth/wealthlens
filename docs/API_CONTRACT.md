# WealthLens API Contract (Phase 1 MVP)

This is the source of truth for endpoint shapes shared between `apps/api`
(Express + TypeScript) and `apps/web` (Next.js). Types referenced below
live in `packages/shared/src` (`@wealthlens/shared`) — both apps import
from there instead of redefining these shapes locally.

Base URL: `NEXT_PUBLIC_API_BASE_URL` (web) / `API_PORT` (api), default
`http://localhost:4000`. All request/response bodies are JSON. All
authenticated endpoints require `Authorization: Bearer <accessToken>`.

Standard error shape for any 4xx/5xx:
```json
{ "error": { "message": "string", "code": "string" } }
```

## Auth

### POST /api/auth/signup
Request: `{ "email": string, "password": string, "name": string }`
Response 201: `{ "user": User, "tokens": AuthTokens }`

### POST /api/auth/login
Request: `{ "email": string, "password": string }`
Response 200: `{ "user": User, "tokens": AuthTokens }`
Response 401 on bad credentials.

### GET /api/auth/me
Auth required. Response 200: `{ "user": User }`

`User` and `AuthTokens` types are in `packages/shared/src/user.ts`.
Password hashing: bcrypt. Token: JWT signed with `JWT_SECRET`, expiry
`JWT_EXPIRES_IN`, payload `{ sub: userId, role }`.

## Linked Sharekhan Account

### POST /api/accounts/link
Auth required. Request body: `LinkAccountRequest` (`apiKey`, `secureKey`,
`clientCode`) from `packages/shared/src/account.ts`.
The API Key and Secure Key are encrypted at rest (AES-256-GCM using
`CREDENTIALS_ENCRYPTION_KEY`) — never returned in any response after this
call. Response 201: `{ "account": LinkedAccountSummary }`.

### GET /api/accounts
Auth required. Response 200: `{ "accounts": LinkedAccountSummary[] }`
(empty array if the client hasn't linked an account yet).

### DELETE /api/accounts/:id
Auth required, must own the account. Response 204.

## Portfolio

### GET /api/portfolio
Auth required. Fetches (via the broker adapter, mock in Phase 1) the
client's holdings + live prices, computed P&L and a sector allocation
breakdown. Also upserts into the `holdings` cache table.
Response 200: `{ "portfolio": PortfolioSummary }` (`packages/shared/src/holding.ts`).

## Recommendations

### GET /api/recommendations
Auth required. Query params: `status` (optional: `pending` | `approved` |
`rejected`). Returns recommendations for the caller's holdings, most
recent first, generated by the rule-based engine against current
portfolio + mock indicator data.
Response 200: `{ "recommendations": Recommendation[] }`
(`packages/shared/src/recommendation.ts`).

### POST /api/recommendations/generate
Auth required. Runs the recommendation engine now for the caller's
current holdings/watchlist and persists new `pending` recommendations
(does not duplicate an already-pending recommendation for the same
ticker). Response 200: `{ "recommendations": Recommendation[] }`.

### POST /api/recommendations/:id/approve
Auth required, must own the recommendation, must be `pending`.
Marks it `approved`, writes an `audit_log` row
(`action: "recommendation_approved"`). Phase 1 does not place a live
order — response indicates the trade is to be executed manually by the
client on Sharekhan, or "pending" if/when order-routing lands in Phase 3.
Response 200: `{ "recommendation": Recommendation }`.

### POST /api/recommendations/:id/reject
Same as approve but sets status `rejected` and logs
`action: "recommendation_rejected"`.
Response 200: `{ "recommendation": Recommendation }`.

## Audit Log

### GET /api/audit-log
Auth required. Response 200: `{ "entries": AuditLogEntry[] }`, most
recent first. Every recommendation generation and every approve/reject
call appends an entry here; entries are never updated or deleted
(insert-only table).

## Notes for both apps

- Frontend calls should go through one small fetch client
  (`apps/web/src/lib/api.ts`) that attaches the bearer token and parses
  the standard error shape — don't scatter raw `fetch` calls across pages.
- Backend must keep the broker integration behind an adapter interface
  (`ShareKhanAdapter` or similar) with a `mock` implementation used by
  default (`SHAREKHAN_ADAPTER=mock`), so a real Sharekhan SDK-backed
  implementation can be swapped in later without changing route handlers.
- Recommendation engine (rule-based v1) rules, at minimum:
  1. Price vs N-day moving average crossover.
  2. RSI threshold (oversold/overbought).
  3. (Optional third rule, e.g. sector exposure cap.)
  Combine into a confidence score (0-1) and a plain-language `reason`
  string per the PRD's example output object.
